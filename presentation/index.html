Einführung

Das Problem: Excel-Chaos im Bewerbungsprozess

Ausgangslage

  • Bewerbungen verteilt auf Excel-Tabs
  • Status, Notizen, Termine schnell unübersichtlich
  • Kein zentraler Blick auf offene Prozesse

Zielgruppe

  • Jobsuchende mit mehreren parallelen Bewerbungen
  • Wunsch nach eigener Kontrolle über die Daten
  • Kostenlos, selbst hostbar (Docker oder AWS)

Ziel der Projektphase: Lauffähiges MVP

• Zielgruppe: alle, die aktiv mehrere Bewerbungen gleichzeitig verfolgen
• Fachbegriff-Erklärung falls gefragt: "Self-hosting" = die Anwendung läuft auf eigener Infrastruktur statt bei einem fremden Anbieter

Architektur

Frontend ↔ Backend ↔ Datenbank

Produktion: gleiche Struktur — CloudFront + S3 · App Runner · RDS · Lambda/EventBridge/SES für die tägliche Automation (alles Terraform-verwaltet)

• Von oben nach unten erklären: Browser lädt die React-SPA, die über den Vite-Proxy /api-Aufrufe ans Backend schickt
• Backend spricht per SQLAlchemy mit Postgres, Alembic hält das Schema versioniert
• Fachbegriff: "Vite-Dev-Proxy" = leitet Anfragen an /api im Hintergrund ans Backend weiter, damit Frontend und Backend im Browser wie eine einzige Adresse wirken
• Auth-Cookie-Pfeil kurz erwähnen: Login setzt ein HttpOnly-Cookie, das der Browser automatisch mitschickt
• Zoom-Plugin: bei Bedarf mit Alt+Klick in einzelne Boxen hineinzoomen, wenn Rückfragen zu einer Schicht kommen
• Letzter Satz zur Produktion nicht vertiefen, nur kurz erwähnen (Verweis auf Terraform).

Tech-Stack

Bewusst schlank gehalten

React 18 + Vite 5

Schneller Dev-Server mit Hot-Reload, kein Build-Warten während der Entwicklung.

FastAPI

Automatische OpenAPI-Doku unter /docs, async-fähig, wenig Boilerplate.

PostgreSQL / SQLite

Postgres in Docker = identisch zur Produktions-DB; SQLite lokal ganz ohne Setup.

Docker + Terraform

Lokale Entwicklung reproduzierbar, AWS-Infrastruktur als Code
Eigene docker start/stop/restart/install-Commands fürs Onboarding.

Lambda + EventBridge + SES

Tägliche Automation ganz ohne eigenen Server; läuft nur, wenn sie wirklich etwas zu tun hat.

Pro Karte höchstens einen Satz sagen, nicht vorlesen. FastAPI kurz einordnen: "Python-Framework, spezialisiert auf REST-APIs, ähnlich zu Express bei Node.js, nur mit eingebauter Validierung."
Lambda-Karte: EventBridge = Cron-Trigger in AWS, SES = AWS-Maildienst zum Versenden. Zusammen: täglicher Check überfälliger Bewerbungen + Mail-Report, ohne dauerhaft laufenden Server.
Docker-Karte: kurz erwähnen, dass die vier Commands Docker/Daemon prüfen, Migrationen abwarten und am Ende alle erreichbaren URLs ausgeben — nicht vertiefen, nur als Beleg für durchdachtes Onboarding.
Falls Zeit fehlt: diese Folie im Zweifel kürzen, nicht die Demo.

Datenbankstruktur

5 Tabellen, klar verknüpft

• Kern-Tabelle: applications, verbindet users und job_postings
• users trägt jetzt zusätzlich die Auth-Felder (password_hash, Timestamps)
• refresh_tokens ist neu für den Login: jede Sitzung ist einzeln widerrufbar (Logout, Passwortwechsel)
• Fachbegriff: "FK" = Foreign Key, eine Spalte die auf die ID einer anderen Tabelle zeigt
• Bei Rückfragen mit Zoom-Plugin (Alt+Klick) in die users- oder applications-Box zoomen.

↓ Details je ein Code-Ausschnitt

Zeitbudget: 1:05 Min. (für alle vier Folien dieses Abschnitts zusammen)
Nur ankündigen, Details folgen auf den nächsten (vertikalen) Folien. Falls Zeit knapp wird: diesen Abschnitt ganz überspringen und direkt zu Herausforderungen springen.

Highlight 1 / 3

Timing-sicherer Login


# Backend/routers/auth.py
password_hash = user.password_hash if user else DUMMY_PASSWORD_HASH
password_valid = PasswordService.verify_password(payload.password, password_hash)

if not user or not password_valid:
    raise HTTPException(status_code=401, detail=GENERIC_LOGIN_ERROR)

Hash-Vergleich läuft immer — auch wenn die E-Mail gar nicht existiert. Verhindert, dass Angreifer per Antwortzeit registrierte E-Mails erraten (“User-Enumeration”).

Fachbegriff: "Timing-Angriff" = aus winzigen Zeitunterschieden einer Antwort auf interne Daten schließen. Hier: ohne Dummy-Hash wäre die Antwort bei falscher E-Mail schneller als bei falschem Passwort — das allein würde schon verraten, welche E-Mails existieren.

Highlight 2 / 3

Migrationen, die auf bestehenden DBs nicht crashen


# Backend/database.py
if current_revision is None and already_has_tables:
    command.stamp(alembic_cfg, "0001_baseline")

command.upgrade(alembic_cfg, "head")

Alembic kam nachträglich dazu. Erkennt automatisch: "Tabellen existieren schon, aber ohne Migrations-Historie" → markiert den Ausgangszustand, statt ihn erneut anzulegen.

Fachbegriff: "Migration" = eine versionierte, nachvollziehbare Änderung am Datenbank-Schema (statt manueller SQL-Befehle). "Stamp" = der DB sagen "du bist schon auf diesem Stand", ohne die zugehörigen Befehle nochmal auszuführen.

Highlight 3 / 3

Serverlose Automation: ein Cron-Trigger genügt


# terraform/eventbridge.tf
resource "aws_cloudwatch_event_rule" "daily_automation" {
  schedule_expression = "cron(0 8 * * ? *)"
}

EventBridge triggert täglich um 8:00 UTC die Lambda (Backend/automation/) — die prüft alle offenen Bewerbungen (OPEN > 7 Tage, IN_PROGRESS > 14 Tage) und verschickt einen HTML-Report per SES. Kein eigener Server läuft dafür durchgehend.

Fachbegriff: "Cron" = Zeitplan-Syntax für wiederkehrende Aufgaben, hier "täglich um 8 Uhr". EventBridge ist AWS' Cron-Dienst.
Deployte Ressourcen kurz aufzählen falls gefragt: aws_lambda_function (Python 3.12), aws_cloudwatch_event_rule (Cron), aws_ses_email_identity (Sender + Empfänger, beide müssen im SES-Sandbox-Modus verifiziert werden), aws_iam_role mit minimalen Rechten (Logs, SES, VPC/RDS), aws_security_group für den RDS-Zugriff.
Empfänger-Adresse (nur für dich als Referenz, nicht auf der Folie zeigen): post@dennis-rapp.com.
Test-Ablauf: DB-Tabellen einmalig anlegen, dann `aws lambda invoke --function-name bewerbungssammler-automation ...` manuell testen, Mail im Postfach prüfen, danach den nächsten automatischen Lauf abwarten (8:00 UTC = 9 oder 10 Uhr deutscher Zeit, je nach Sommerzeit).

Herausforderungen

3 Probleme, 3 Lösungen

❌ Problem

Kein Migrationstool, aber Schema musste sich rückwirkend ändern.

✅ Lösung

Alembic eingeführt, inkl. automatischer Erkennung bestehender Datenbanken.

❌ Problem

Login könnte verraten, welche E-Mails registriert sind.

✅ Lösung

Generische Fehlermeldung + Dummy-Hash-Vergleich, timing-sicher.

❌ Problem

PowerShell-Skript brach mit kryptischer Fehlermeldung ab.

✅ Lösung

Ursache gefunden (Fehlerbehandlung), saubere Meldung + Exit-Code.

Zeitbudget: 1:10 Min.
• Problem 1: Bestehende User-Datensätze durften beim Hinzufügen der Passwort-Spalte nicht verloren gehen → Platzhalter-Hash für Altdaten, die dann manuell zurückgesetzt werden müssen
• Problem 2: Sicherheitskonzept "User Enumeration" kurz in einem Satz erklären: nach außen darf nicht sichtbar sein, ob eine E-Mail existiert
• Problem 3: reale Debugging-Geschichte aus der Docker-Skript-Entwicklung — zeigt Fehlersuche in der Praxis, nicht nur am Reißbrett
• Diese drei sind alle direkt am Code/Verlauf nachvollziehbar, keine erfundenen Beispiele.

Ausblick

Was als Nächstes ansteht

  • Mail-Infrastruktur (SES) existiert bereits für Automation-Report. E-Mail-Verifizierung & Passwort-Reset könnten darauf aufbauen
  • Mit Route 53 Domain holen

Wichtige Nuance: SES ist aktuell nur für die Automation-Mails eingerichtet (Sender/Empfänger müssen einzeln in SES verifiziert werden, Sandbox-Modus). Für Auth-Mails wäre das derselbe Baustein, aber noch nicht verdrahtet — bewusste Entscheidung, kein technisches Versäumnis (siehe README, Abschnitt "Aktuelle Einschränkungen").
